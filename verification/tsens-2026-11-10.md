# Read-only TSENS telemetry verification

Baseline kernel `c38903d4`, branch `feat/pixel-driver-support`. This change adds
SDM670 TSENS v2 telemetry only, a `thermal` monitor command, a registry entry and
the neoui Thermal catalogue mapping. No trip, calibration, reset, IRQ, regulator
or throttling writes are made. `partial` registry state means telemetry only.
Unmapped/unsupported version and disabled/invalid samples return errors without
changing the caller's output. Reads are bounded to three status samples.

Register semantics were checked against Linux `drivers/thermal/qcom/tsens-v2.c`
and `tsens.c`; code is original Apache-2.0 implementation. Controller addresses
and 13/8 sensor counts come from the supplied private Bonito DTB. Sensor numbers
are controller-local, not independently established CPU/core temperature labels.

## Phone acceptance

Subsequent host enumeration detected the connected Pixel. Ran the private test
image using `phone.py run boot.img --cmd thermal --cmd drivers --secs 10 --no-date`
(with paths under the private artifact root), exit **0**. No image was flashed;
the kernel-only image left EMMC_C unset and returned to fastboot afterward.

All **21/21 sensors** returned valid samples, **32500..33800 milli-Celsius**
(32.5..33.8 C). The registry entry was `thermal`, state `partial`, driver
`qcom_tsens`, detail `21/21 valid; max 33800 mC; read only; no thermal policy`.
This validates register access and reporting, not independent temperature accuracy
or physical CPU/core labels. Kernel/user smoke completion markers are retained
in the boot log.

Raw files: `phone-kernel.log`, `phone-command.log`, `phone-command.json` and
`phone-result.json` in the private artifact root. The earlier zero-device check
was superseded by this successful test.
