# Rust integration: the `e32` crates and the Rust UI

Part of [User side](README.md) · Status: done · Updated: 2026-11-25

Written 2026-11-06 as the plan for Track U of the [roadmap](../roadmap.md). Its stages R0–R10 and H3a were done by
2026-11-12. This page says what Rust on the user side is now, what is still open, and keeps the kernel calls neoui
uses. The record of each stage moved to [history/rust-stages.md](history/rust-stages.md) on 2026-11-27; each stage
heading below keeps a short summary and a link.

## Rust on the user side now

- **The crates** are in [NeoSymbian/e32-rs](https://github.com/NeoSymbian/e32-rs):
  - `e32-sys`: raw exec calls (`svc` with the fast/slow bit) and the ABI types (`TDesC8`/`TDesC16`, handles,
    `TRequestStatus`). Its `execs.rs` is generated by `tools/gen_execs.py` from the kernel's `execs.txt`; all 315
    numbers match the 2010 `genexec.pl`.
  - `e32`: the safe API: heap, threads, `sync::Mutex` (a kernel mutex that refuses re-entry), timers, an async
    executor on request statuses, the file server (`e32::fs`, file handles shared between processes), and
    `e32::server`, the Rust `CServer2`.
  - the NeoEcho test service `neoecho`, the test programs (`neotest`, `neosrv`, `neor1`, `neopanic`, `rust-hello`,
    `neowb1`, `neocpu`) and the C++ checks `symbian/neocli.cpp`, `neotrap.cpp`, `neobench.cpp`.
- **The target** is ARMv8-A AArch32 with the soft-float calling convention (US4, 2026-11-25:
  [user-side-smp.md](user-side-smp.md#us4-results-2026-11-25)): `targets/armv8a-neosymbian-eabi.json` (no_std) and its
  std twin `armv8a-symbian-eabi.json` (the browser). Every Symbian workspace keeps a byte-identical copy of the no_std
  target; `cargo arm` builds it with `-Zbuild-std` on the pinned nightly (`rust-toolchain.toml`), and `cargo clippy-arm`
  runs clippy on it. **Never an `eabihf` target:** it passes floats in VFP registers and breaks every call into a
  Symbian library. Keep one e32 revision per EXE across the pins.
- **Who uses it:** neoui (the UI server `SYSSTART.EXE` and its apps), phone, files, datetime, neohw (the hardware
  daemons) and the browser (std, through `cargo sym`).
- **Into the ROM:** a Rust EXE is a staticlib (`lib<name>.a` from `cargo arm`, in
  `target/armv8a-neosymbian-eabi/release`) plus one line in NeoSymbian/build's `rust/exes.txt`:
  `NAME.EXE uid3 lib.a|- [glue.cpp] [drive=c]` (`-` = C++ only). `emitter/build_rust_exe.py` links it with the EXE
  start-up into an E32 image when `neo rom` runs. Each repo's `symbian/exes.txt` lists its lines.
  - EXEs go in the ROM by default; `drive=c` puts one on C: (loading from C: works since build `c6b0b10`).
  - ROM EXEs get every capability, `drive=c` ones none. ROM EXE names are 8.3 (`NEODEV.EXE`).
- **Where it is tested:** e32-rs's `virt` CI boots the ROM on QEMU `virt` with our AArch64 kernel and runs R0–R3,
  NEOWB1, NEOTRAP and NEOCPU; then the Pixel. Syborg was the test platform until 2026-11-21.

## Why this works now

On 2026-11-06 the Rust stream started on Phorepoc's `symbian-2010` (now NeoSymbian/build), the 2010 user side booted
in QEMU Syborg, with the same ABI as the phone's user side, so one binary ran on both. Syborg was dropped on
2026-11-21; see [the record](history/rust-stages.md#why-this-works-now).

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Rust target | **ARMv8-A AArch32 softfp since US4** (`targets/armv8a-neosymbian-eabi.json`, e32-rs; [user-side-smp.md](user-side-smp.md)); before 2026-11-25 `armv5te-none-eabi`. A pinned nightly (`rust-toolchain.toml`, `-Zbuild-std`), with `panic=abort` | Exact match of the user-side ABI, so it runs on the Pixel and on QEMU `virt`. **Never `eabihf`:** it passes floats differently and breaks calls into Symbian libraries. |
| Test platform | QEMU `virt` with our AArch64 kernel (CI), then the Pixel. QEMU Syborg until 2026-11-21 | `virt` boots the same user payload as the phone (US6a/US6b) |
| CI | GitHub Actions on the public repos, with the `ghcr.io/neosymbian/toolchain` image. Screenshots and serial logs kept as artifacts; no ROM images (Slint is GPL-3.0) | Progress is visible to everyone |
| Kernel interface | Rust makes **exec calls directly** (`svc`), with the table generated from the kernel's `execs.txt`. Features that exist only in euser's C++ (leaves, `TRAP`, the active scheduler) go through a thin C shim, and only when unavoidable. | No C++ name mangling; no leave or unwind ever crosses into Rust |
| Entry point | Rust defines `E32Main` (`#[export_name = "_Z7E32Mainv"]`), linked with build's `efile_exe` start-up | Behaves like any other Symbian EXE |
| Repos | New: **`NeoSymbian/e32-rs`** (system crates) and **`NeoSymbian/neoui`** (UI server and apps); later phone, files, datetime, neohw, browser. The build is NeoSymbian/build (was the `symbian-2010` fork); `qemu-syborg` is [retired](../history/retired-repos.md) | New work goes in new repos; dependencies are forked |

## Open items

- **The UI toolkit's licence** (decided 2026-11-06 for development only): Slint under GPL-3.0, so `neoui/symbian` and
  the apps linking it are GPL-3.0 and ROM images are not published.
  - Slint is available under GPL-3.0, a royalty-free licence, or a commercial licence.
  - The royalty-free licence excludes embedded systems, which an OS launcher or UI server may count as.
  - Under GPL-3.0, an image that combines it with EPL-1.0 Symbian code may not be distributable, because the two
    licences are incompatible.
  - Decide before any release: Slint's commercial licence, or a permissive renderer (our own, or
    `embedded-graphics`) behind the same `neoui-render` API.
- **Dev tools request 3** ("Share E: over USB", [above](#dev-tools-and-boot-ok-kernel-calls-for-neoui-requests-from-the-kernel-stream-2026-11-08)):
  waits for [FS6](../storage/filesystem.md#fs6-usb-mass-storage), which is researched but not started.

## Risks

- **The target is our own JSON spec** (`armv8a-neosymbian-eabi.json`). It needs nightly plus build-std, so the
  nightly stays pinned (`rust-toolchain.toml`), the same in every repo.
- **Only one process can capture the kernel's event hook.** The UI server holds it; the old apps' guest window
  server takes no event-hook ownership ([legacy.md](legacy.md#architecture)).
- **QEMU `virt` runs under TCG** and orders memory more strongly than the Pixel: it proves that things work, not how
  fast they are or that they are SMP-safe. The phone stays the real test.
