# Battery telemetry implementation verification — 2026-11-11

This implements [read-only battery telemetry](../battery-telemetry.md) on the
`feat/pixel-driver-support` branch. Existing thermal changes and unrelated fshell
files are preserved. No commit or phone installation is implied by these results.

## Implemented

- PM660 identity/readiness and direct coherent gauge/charger observations, bounded
  retries, 64-bit voltage conversion, serialized SPMI observer transactions.
- ReadDeviceData-gated HAL 0x4e1a, 32-byte versioned snapshot with independent
  validity; `battery` monitor diagnostics and device-registry entry.
- Typed Rust decoding, five-second polling, status bar, Settings battery page,
  24-hour percentage graph and Dev tools integration.
- Bounded minute history, checksums and two alternating private C: files; save
  every five minutes and before normal restart/fastboot/shutdown. Missing data
  and clock/reboot discontinuities are gaps; corrupt copies are rejected.

No PMIC configuration, charge/profile initialization, ADC trigger, watchdog kick
or firmware change is introduced. The displayed percentage is the accepted
hardware-reported estimate; profile integrity and hardware sample age remain
unverified. Historical files contain observations, not generated demo data.

## UI, USB and history acceptance

The live Battery details were visually inspected in `phone-battery-first.png`: 96%,
Full, USB Connected, 4.248 V and a graph beginning with actual samples. The user
confirmed that disconnecting USB for 15 seconds changed the page to Discharging.
After reconnect, the monitor reports validity `0x3f`, USB present/online and Full
again (`phone-after-reconnect.log`). The disconnected screen was user-observed;
it was not captured through the disconnected USB console.

Dev tools was visually verified in `phone-devtools-lower.png` and
`phone-devtools-battery.png`: qcom_battery Partial, 96%, 4.249 V, USB Connected,
Full and read-only/profile-unverified facts. Its check passed on target.
The first RAM session was ended with Dev tools → Tools → Restart to fastboot
and its confirmation, exercising the UI battery-save path before clock/drive
finalization. `phone-normal-fastboot.log` records the UI action; fastboot returned
within the bounded check. The next RAM boot restored those observations, as recorded below.

The user additionally requested connected/charging state in the status bar. That
increment adds a USB plug, active-charge lightning and a full check (full requires
valid online USB power), leaving discharging neutral. The final matching candidate is
`private/driver-support/battery-20261111/ui/boot.img`, 7,888,896 bytes, SHA256
`4c28073e44419b869f6ba555f71aaf90ff5e9046faae287b8f3b1055a03760ae`.
Its nine checks in `ui-status-checks.json` all exit **0**: 103 model tests,
focused status-render regression, host/ARM Clippy, ARM workspace build, formatting,
diff check and isolated RAM image build (94 OK / 0 FAIL). Final source hashes:
`ui/provenance.json`. An independent status/logging review found no actionable
findings; long-title plus modem/RAT combinations lack a focused layout assertion.

The final candidate's second RAM boot exits **0**. `phone-second-run.log/.json`
and `phone-second-boot.log` record actual PMIC validity `0x3f`, 96%, 4,249,744 uV,
USB present/online, Full, and:

```text
battery: history restored gen=2 points=8 storage_error=false
battery: valid=0x3f usb=1/1 charge=4
```

The final screenshot `phone-status-full.png` was visually inspected: USB plug,
full check inside the battery and green 96% are visible. After the final unplug
and reconnect, `phone-status-transition.log` records:

```text
battery: valid=0x3f usb=1/1 charge=4
battery: valid=0x3f usb=0/0 charge=1
battery: valid=0x3f usb=1/1 charge=4
```

The user reported the new behavior was good. This confirms connected/full →
disconnected/discharging → connected/full on the actual phone. Active charging
(state 2 / lightning) is covered by host tests; the phone reported Full during
these connected observations, so active-charge hardware behavior was not observed.

This demonstrates that the first session's real observations survived a normal
fastboot restart on existing C:.

## Remaining limits

Real file-I/O failures are **not passed** by host model checks. Normal reboot restoration and corrupt-copy model checks do not
establish power-cut durability. The last five minutes may be lost after an abrupt
reset; a filesystem failure can impose additional limits.

Earlier product-handshake failures occurred before boot; preserved evidence is
`phone-connection.json` and `preflight.log`. They were resolved by reconnecting
USB and are separate from the successful RAM boot above.
